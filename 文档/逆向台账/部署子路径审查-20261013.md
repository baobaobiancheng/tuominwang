
## 资源约束和真实运行门

1. 常驻容器限制分别 DB128MiB、API512MiB、worker1200MiB、web48MiB，总计1888MiB；这些是上限，不是预留，也不代表2GiB宿主同时容纳所有服务峰值。还需计入既有WeKnora、宿主和swap。maintenance不是常驻服务，但迁移/建账号时也占用资源。
2. 本地amd64证据 `.data/deploy/aliyun-20261013/capacity-amd64.log` 报告离线NER与PDF/OCR/新PDF验证通过，峰值RSS970472KiB，cgroup1221369856字节。对应container记录exit0/OOMKilled=false。这是单个离线样本，不是云端全栈常驻/并发/长期验收。
3. worker与API通过数据库advisory lock限制指定重任务；`runProcessing` 的view/page/preview/gate/download等未全部经过该锁。不能把“单重任务”描述成整个应用只能同时运行一个处理线程。
4. API容器512MiB内还会起处理线程；线程JS老生代上限512MiB，此外还有父进程/年轻代/native内存。容器OOM与线程可捕获OOM是两类故障，当前线程错误处理不等于容器不会重启。
5. web内存48MiB，tmpfs64MiB，允许约50MiB上传。两层代理均新增 `proxy_request_buffering off` 且使用 HTTP/1.1，避免先把整份上传请求体缓冲到 web tmpfs；`proxy_buffering off` 单独控制响应缓冲。请求将流向 API 接收端，不能据此认为上传内存占用消失，也不能以 GET 健康检查通过代表上传容量通过。
6. memswap_limit为memory+swap总量限制，不证明宿主已配置且可用的swap。真实峰值受模型页缓存、输入页数/图片尺寸、原站点负载影响。

上线后记录：空闲各容器RSS/cgroup、宿主MemAvailable/swap；一份真实范围合成NER材料；PDF/OCR→复核→预览→导出→下载；接近允许大小的上传；处理期间原站点页面/API可用性；Docker OOMKilled/重启次数、任务lease和失败恢复。若触发限制，应根据实际触发环节调资源/容量或排队，不将失败忽略为“部署成功”。本报告未执行这些运行测试。
